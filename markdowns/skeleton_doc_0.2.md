# LeafOS 0.2 Design Skeleton

Status: complete
Version: 0.2.0
Codename: Universal CLI Task Pipeline

## 1. Purpose

LeafOS 0.2 proves a reliable command-line task pipeline without requiring a
live model. A user can describe a task, generate a plan, preview the plan,
execute it with explicit confirmation, and receive a report.

The 0.2 design is intentionally small. It establishes the control surface,
file contracts, execution boundary, and completion gate used by later graph,
coder, relay, and hosting layers.

## 2. Design Principles

- Boring and useful beats clever and broken.
- Files are the state carrier.
- The CLI is the control surface.
- Plans must be inspectable before execution.
- Execution requires explicit confirmation.
- Every successful run leaves a report.
- The same task flow should work across supported shells and platforms.

## 3. Core Spine

```text
human request
    -> agent-task
    -> task file
    -> agent-route --mock
    -> generated plan
    -> agent-dry-run
    -> agent-run --yes
    -> agent-report
```

## 4. Primary Commands

```bash
leafctl agent-task "create a hello world C project"
leafctl agent-route tasks/create-a-hello-world-c-project.md --mock
leafctl agent-dry-run tasks/create-a-hello-world-c-project.generated.plan.sh
# Optional machine-readable previews:
leafctl agent-dry-run tasks/create-a-hello-world-c-project.generated.plan.sh --plain
leafctl agent-dry-run tasks/create-a-hello-world-c-project.generated.plan.sh --json
leafctl agent-run tasks/create-a-hello-world-c-project.generated.plan.sh --yes
leafctl agent-report 0.2.0
```

Supporting inspection and health commands:

```bash
leafctl doctor
leafctl status
leafctl platform
leafctl versions
leafctl provider-status
```

## 5. Component Boundaries

```text
bin/leafctl                 CLI entrypoint and command routing
bin/leafctl.ps1             PowerShell forwarding surface
core/agent/                  task, route, dry-run, run, and report behavior
core/providers/              mock and external provider adapters
core/plan/                   plan generation and validation
core/system/                 platform, path, and version helpers
tasks/                       human-authored task files
runs/                        execution state and run artifacts
reports/                     human-readable completion reports
tests/                       spine, smoke, compatibility, and layer tests
```

The exact implementation may span additional helper files, but these
responsibilities should remain recognizable and independently testable.

## 6. File Contracts

### Task file

```text
tasks/<task-slug>.md
```

Required content:

- title
- scope
- steps or requested outcome

The task file is human-readable and is the durable input to routing.

### Generated plan

```text
tasks/<task-slug>.generated.plan.sh
```

Required behavior:

- contains generated-plan metadata
- includes the `LEAFOS_AGENT_PLAN=1` marker
- includes the 0.2.0 plan version when generated by LeafOS
- can be validated before execution
- can be printed during dry-run
- supports normal, plain, and JSON dry-run output
- exits nonzero when validation fails
- does not execute merely because it was generated

### Run state

```text
runs/<run-id>/
```

May contain provider responses, normalized plan data, command output, and
execution status. Run artifacts should be append-friendly and inspectable.

### Report

```text
reports/<run-id>.md
```

The report records the task, plan outcome, executed actions, failures, and
completion status.

## 7. Execution Contract

The normal 0.2 path is:

1. Create or receive a task file.
2. Route the task through the mock provider or configured provider adapter.
3. Normalize the response into a generated plan.
4. Validate the plan.
5. Show the plan during dry-run in normal, plain, or JSON form.
6. Require an explicit `--yes` confirmation for execution.
7. Run bounded commands in the selected work directory.
8. Write a report regardless of success or failure.

No step should silently turn a dry-run into an execution.

Generated task and plan files are written through temporary files and moved
into place only after validation. Existing task and plan paths are never
overwritten.

## 8. Provider Boundary

The provider layer accepts a task and returns plan material. 0.2 must work in
mock/offline mode and should expose clear status when an external provider is
unavailable or missing credentials.

Supported adapter direction:

```text
mock/offline
OpenAI-compatible provider
Anthropic-compatible provider
DeepSeek-compatible provider
local llama.cpp-compatible provider
```

Live model reasoning, graph creation, and coder patch generation are deferred
to later versions. The 0.2 provider boundary exists so those additions do not
need to replace the CLI pipeline.

## 9. Safety Rules

- No execution without explicit confirmation.
- Dry-run must be side-effect limited to preview artifacts.
- Plan validation must fail closed on malformed input.
- Commands must run from a known work directory.
- Paths must be normalized before file operations.
- Provider failures must be visible and return meaningful status.
- Reports must distinguish planned, attempted, successful, and failed work.

## 10. Platform Surface

The design targets:

```text
macOS       Bash, Python, PowerShell, C compiler
Linux       Bash, Python, PowerShell, C compiler
WSL         Bash, Python, PowerShell, C compiler
Windows     Git Bash or MSYS2, Python, PowerShell 7+, MinGW C compiler
```

The Bash surface is the reference implementation. PowerShell forwarding and
platform helpers preserve command intent across supported environments.

## 11. Completion Gate

The 0.2 release is complete when the spine test passes end to end:

```bash
./tests/spine.sh
```

Expected proof:

```text
task created
plan generated
plan validated
dry-run preview shown
execution completed only after confirmation
report written
```

Additional 0.2 regression coverage:

```bash
./tests/agent_0_2.sh
./tests/powershell_0_2.sh
```

## 12. Explicitly Deferred

The following belong to later versions:

- Brain-generated agent graphs
- Dependency-aware graph execution
- Embedded agentic actions and soft waits
- Coder-generated unified patches
- Repair-node injection and node replay
- Distributed nodes and efficient relays
- Continual hosting and adaptive hardware utilization
- Dataset export and multi-agent lanes

## 13. Extension Point

The 0.2 pipeline is the trunk for the later system:

```text
0.2  CLI task pipeline
0.3  brain + graph
0.4  actions + coder patches
0.5  telemetry + repair
0.6  templates + hosting foundation
0.7  nodal deployment + relays
0.8  continual hosting + dataset export
0.9  stable local agentic project builder
```

Later layers should add capability behind the existing task, plan, run, and
report contracts wherever practical.
