## Objective

Prove that LeafOS behaves as one program by running a retained project through inspection, typed planning, deterministic allocation, live inference, execution, validation, evidence, CCIS gating, replay/recovery, and explicit acceptance.

## Relationship to LOOP1

LOOP1 defines the one-to-one surface; LOOP2 defines commands and `plz`; LOOP3 defines resources; LOOP4 defines results. LOOP5 is their joint acceptance demonstration and freezes only what is actually proven.

## Live-inference intent

The success path includes actual local GGUF generation through the WO-054/WO-055 runtime, not mock transport. Live inference remains bounded, resource-claimed, evidence-classified, and unable to accept or mutate the canonical project by itself.

## Typed task contract

- `system.loop_demonstration.v1` is a composite verification task whose children retain their own registered types and evidence.
- Inputs bind fixture baseline commit/hash, command registry, task registry, resource policy, renderer policy, model/binary/grammar digests, and acceptance authority.
- Results enumerate every canonical node, transition event, command observation, evidence artifact, resource delta, recovery proof, and final project hash.
- The freeze record lists proven contracts, provisional contracts, failures, deferred items, and exact registry/schema digests.

## LOOP6 test adoption

LOOP5 proves the coherent demonstration mechanics; [LOOP6](WO-LOOP6-real-repository-scientific-outcome-tests.md) owns the real test ledger. LOOP5 must prepare C01/C08/C09 paths and the recommended T01–T08 pack without marking any LOOP6 result passed until its retained evidence is verified.

## Acceptance criteria

- [ ] A retained `[project.example]` fixture begins from a clean committed baseline with immutable starter materials.
- [ ] `leafos project inspect`, `plz plan`, `plz run`, `plz status`, allocation verify, evidence verify, `plz accept`, and final project status form one documented path.
- [ ] A canonical `leafos task` dry-run/equivalence check proves the `plz` path creates the same typed task digest and result semantics.
- [ ] At least one bounded child task performs live local GGUF inference and retains real prompt, output, timing, model/backend, resource, and cleanup evidence.
- [ ] The success path produces complete typed task, candidate, plan, allocation, command, validation, evaluation, decision, transition, and result evidence.
- [ ] The canonical project and Git index remain unchanged until explicit digest-bound acceptance.
- [ ] An interruption path deletes disposable projections, replays events, reconstructs ordering/leases/state, and resumes without manual repair.
- [ ] A rejection path restores the original project hash and retains diagnostic evidence.
- [ ] Human, JSON, diagram, event, allocation, and evidence views agree on every canonical state and legal next action.
- [ ] The final freeze report marks no feature integrated unless it is reachable through the main CLI and both deterministic and live acceptance gates pass.

## Implementation sequence

1. Select and hash the retained fixture, host facts, llama.cpp binary, GGUF, grammar, and all registry/schema policies.
2. Reserve complete implementation, validation, evidence, rollback, integration, interface, and human-review budgets.
3. Run the canonical inspection and `plz` planning path; compare it with canonical task-command semantics.
4. Allocate and execute the bounded live-inference child plus isolated project mutation/validation tasks.
5. Verify evidence, gate the candidate, and prove no pre-accept canonical mutation.
6. Interrupt a second run, delete caches, replay, resume, and verify lease/resource recovery.
7. Reject and hash-verify rollback on a third path.
8. Explicitly accept the successful candidate and verify idempotent repeat acceptance.
9. Render and compare CLI, JSON, diagrams, events, allocation, evidence, and final project state.
10. Publish the freeze report and hand the retained run identities to LOOP6 for outcome verification.
